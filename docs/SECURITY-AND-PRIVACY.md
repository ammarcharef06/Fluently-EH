# الأمان والخصوصية — Fluently

## 1. الهدف
حماية حسابات المتعلمين وبياناتهم وتقدمهم ولوحة الإدارة وحزم المحتوى، مع تقليل جمع البيانات وتوضيح حدود الحذف والعمل دون اتصال.

## 2. مبادئ الخصوصية
- جمع أقل قدر لازم لتقديم الوظيفة.
- لا إعلانات ولا تتبع تسويقي.
- لا تسجيل لصوت المتعلم ولا تقييم آلي للنطق.
- لا إرسال لإجابات المتعلم أو محتوى الدرس ضمن تقارير الأعطال.
- إتاحة تصدير بيانات المتعلم وحذف الحساب.
- الإحصائيات التفصيلية للإدارة مقيدة بالدور وتُستخدم لأغراض المنتج والتعليم.
- لا تُعرض بيانات المتعلم في روابط عامة أو سجلات غير محمية.
- لا يُطلب تاريخ ميلاد دقيق إلا عند وجود ضرورة قانونية موثقة.
- العمر اختياري حيثما أمكن؛ تُطبّق موافقات ولي الأمر والقيود حسب قانون بلد الإطلاق.

## 3. بيانات يجب تصنيفها
- **عامة:** الشيفرة والوثائق ومحتوى منشور مرخص.
- **حساب:** البريد، معرف مزود الهوية، الاسم المستعار، حالة التحقق.
- **تعليمية:** المستوى، التقدم، المحاولات، الأخطاء، الخطة والمراجعة.
- **إدارية:** الأدوار والدعوات والمراجعات وسجل التدقيق.
- **أسرار:** مفاتيح API واتصالات قاعدة البيانات ومفاتيح توقيع الجلسات والحزم.
- **تشخيصية:** بيانات الأعطال الاختيارية التي لا تتضمن إجابات أو بيانات شخصية.

يُحدد لكل فئة غرض وصلاحيات ومدة احتفاظ وآلية حذف وتصدير.

## 4. المصادقة والجلسات
- Google أو البريد وكلمة المرور.
- تأكيد البريد للحسابات ذات كلمة المرور قبل المزامنة.
- استعادة عبر رابط أو رمز.
- أول تسجيل دخول يتطلب الإنترنت.
- كلمات المرور لا تُخزن كنص صريح؛ تستخدم خوارزمية مخصصة لكلمات المرور مثل Argon2id بإعدادات معتمدة عند التنفيذ.
- لا تُرسل كلمة المرور إلى السجلات.
- رموز الجلسات تُخزن وفق آلية المنصة الآمنة؛ لا تضع أسرارًا دائمة في localStorage.
- جلسة Offline المحفوظة محدودة الصلاحية والسياسة، ولا تمنح وصولًا إداريًا.
- تغيير كلمة المرور أو حذف الحساب أو سحب الهوية يؤدي إلى إبطال الجلسات حسب السياسة.
- تحديد محاولات الدخول ومنع التخمين الآلي.

مزود الهوية والبريد لم يُعتمدا بعد؛ لا يختار أي مزود قبل إثبات عدم وجود تجربة مؤقتة أو بطاقة/فوترة غير مقصودة.

## 5. التفويض والأدوار
الأدوار:
- مدير رئيسي.
- محرر محتوى.
- مراجع.
- مسؤول نشر.
- متعلم.

تُطبق صلاحيات كل عملية على الخادم وفق مبدأ أقل صلاحية. يجب التحقق من ملكية السجل أو نطاق المؤسسة لكل طلب لمنع الوصول الأفقي. لا يُعتبر إخفاء الأزرار في الواجهة تفويضًا.

عمليات عالية الحساسية:
- إنشاء/تعطيل موظف.
- تغيير دور.
- الاطلاع على بيانات متعلم فردية.
- تصدير بيانات.
- تعديل محتوى منشور.
- اعتماد محتوى.
- نشر حزمة.
- استرجاع إصدار.
- حذف حساب أو بيانات.

تُسجل هذه العمليات في audit log مع الفاعل والوقت والهدف والنتيجة، دون نسخ أسرار أو حمولة شخصية كاملة.

## 6. اختيار المالك للتخزين المحلي
اختار مالك المشروع عدم فرض تشفير شامل لبيانات التعلم المحلية في النسخة الأولى. هذا يترك احتمال قراءة بعض الملفات لمن يملك وصولًا مباشرًا إلى الجهاز أو ملفاته.

لا يعني ذلك:
- تخزين كلمات المرور محليًا.
- حفظ أسرار الإدارة أو مفاتيح الخادم.
- وضع رموز وصول طويلة العمر في localStorage.
- تصدير بيانات مستخدم إلى حزمة المنهج.

يجب استخدام مخزن النظام الآمن للرموز الحساسة عند دعم المنصة، وتوضيح مخاطر الجهاز المشترك أو غير المحمي.

### الهوية المحلية المجهولة في Windows
- UUID v4 المخزّن في SQLite هو معرّف محلي مستعار لربط تقدم قاعدة التطبيق على الجهاز نفسه؛ لا يثبت هوية شخص ولا يمثل حسابًا أو جلسة مصادقة أو تفويضًا سحابيًا.
- ينشئه Rust/Tauri من مولد عشوائي آمن، ولا تقبل أوامر التقدم معرّفًا يرسله WebView. يظل التحقق من ملكية الحساب السحابي وتفويض API مسؤولية الخادم عند إضافة المزامنة.
- استيراد تقدم IndexedDB السابق يتم مرة واحدة في معاملة SQLite ذرية تحت الهوية المحلية. لا تُعاد نسبة صفوف SQLite القديمة إلى الهوية الجديدة تلقائيًا.
- أمر مسح بيانات التعلم المحلية يحذف جميع صفوف تقدم SQLite، بما فيها الصفوف القديمة المحفوظة أثناء الترحيل، ثم يحذف صف الهوية نفسه. لا يحذف هذا الأمر حسابًا سحابيًا؛ حذف الحساب وإبطال الجلسات يبقيان مسارين منفصلين.

## 7. حماية API
- TLS في النقل.
- تحقق مخطط لكل مدخل.
- حدود حجم الطلب والملف.
- تحديد معدل حسب المسار والحساب وIP عند ملاءمة الخصوصية.
- منع IDOR عبر فحص ملكية الموارد.
- حماية CSRF عند استخدام cookies.
- CORS مقيد للنطاقات المطلوبة.
- رؤوس أمان الويب المناسبة.
- منع SQL injection باستخدام معاملات/استعلامات آمنة.
- ترميز مخرجات النص لمنع XSS.
- عدم تنفيذ HTML أو JavaScript اعتباطي داخل حزم الدروس.
- حماية SSRF وURL fetching إن أضيفت وظيفة جلب روابط.
- أخطاء API لا تكشف stack traces أو معلومات اتصال.

## 8. حماية حزم المحتوى
- manifest موثوق يحدد الإصدار والمتطلبات والملفات.
- تحقق من SHA-256 أو بصمة مناسبة لكل ملف.
- توقيع رقمي للحزمة/manifest باستخدام مفتاح إصدار خاص محفوظ خارج المستودع.
- المفتاح العام أو آلية الثقة موزعة مع التطبيق.
- رفض الحزم غير الموقعة أو غير المتوافقة أو المعدلة.
- منع Zip Slip ومسارات اجتياز المجلدات.
- منع الملفات التنفيذية والروابط الرمزية والملفات ذات المحتوى النشط غير المصرح به.
- حدود للضغط وفك الضغط وعدد الملفات والحجم الكلي لمنع zip bombs.
- المحتوى المستورد يدخل مسودات الإدارة ولا ينشر مباشرة.

## 9. أمن سلسلة التوريد
- تثبيت الإصدارات واستخدام lockfile.
- فحص التبعيات والثغرات قبل الإصدار.
- مراجعة الرخص والتبعيات.
- تجنب مكتبات غير ضرورية أو مهجورة.
- عدم إضافة خدمة خارجية قبل فحص شروطها.
- حماية GitHub Actions وأسرار النشر.
- توقيع ملفات الإصدارات عند القدرة، وتوثيق حالة التوقيع إن لم تتوفر شهادة موثوقة.

## 10. حذف الحساب والتصدير
عند طلب الحذف:
1. التحقق من هوية صاحب الطلب.
2. تسجيل الطلب وحالته.
3. إبطال الجلسات.
4. منع مزامنة جديدة للحساب.
5. حذف بيانات الحساب السحابية وفق جدول الاحتفاظ القانوني.
6. حذف أو فصل البيانات التعليمية بحسب السياسة القانونية والغرض.
7. معالجة بيانات النسخ الاحتياطية ضمن دورة الاحتفاظ.
8. إرسال أمر حذف للأجهزة التي تتصل لاحقًا.
9. توضيح أن الجهاز الذي بقي Offline لم يؤكد الحذف المحلي بعد.

لا يوعد المستخدم بحذف فوري من جهاز غير متصل أو من نسخة احتياطية قبل انتهاء فترة احتفاظ معتمدة.

## 11. النسخ الاحتياطية
اختار المالك النسخ التشغيلي اليدوي عند الحاجة. يجب:
- توثيق المسؤول وخطوات النسخ.
- إجراء نسخة قبل تغيير مخطط أو إصدار كبير.
- التحقق من اكتمال النسخة وسلامتها.
- اختبار استعادتها دوريًا.
- حفظها في مكان منفصل ومحمي.
- عدم اعتبار وجود نسخة غير مختبرة ضمانًا للاستعادة.

هذه السياسة تحمل خطر فقدان البيانات بين النسخ؛ يجب إظهاره بوضوح قبل الإطلاق الإنتاجي.

## 12. تقارير الأعطال
اختيارية وبموافقة المستخدم، ولا تتضمن:
- محتوى الدرس أو نصوص إجاباته.
- كلمات المرور أو الرموز.
- الاسم أو البريد أو بيانات شخصية.
- تسجيلات صوتية.
يمكن إرسال إصدار التطبيق والمنصة ونوع الخطأ ومكدس تقني منقح بعد إزالة المسارات والمعرفات الحساسة.

## 13. نموذج التهديد الأولي
أصول يجب حمايتها:
- حسابات المستخدمين.
- بيانات التقدم ونتائج الاختبارات.
- بيانات الإدارة وسجل التدقيق.
- محتوى المنهج والحزم.
- مفاتيح التوقيع والأسرار.

تهديدات أساسية:
- سرقة حساب أو جلسة.
- وصول موظف يتجاوز دوره.
- تعديل تقدم أو سؤال عبر API.
- حزمة منهج معدلة أو خبيثة.
- تسرب بيانات عبر logs/crash reports.
- فقد بيانات محلية أو تعارض مزامنة.
- اعتماد محتوى خارجي دون حق توزيعه.
- استنفاد حصص الخدمة المجانية أو تعطيلها.

## 14. شروط قبول الأمان والخصوصية
- لا أسرار في المستودع أو ملفات التطبيق.
- جميع عمليات الإدارة مفوضة على الخادم.
- اختبارات لملكية السجلات والصلاحيات.
- لا كلمات مرور نصية أو رموز دائمة في localStorage.
- حزم المنهج تُفحص بصماتها وتوقيعها قبل التفعيل.
- تقارير الأعطال لا تتضمن إجابات أو بيانات شخصية.
- طلب حذف الحساب يبطل الجلسات ويعالج التخزين المركزي والمحلي وفق الاتصال.
- لا يوجد تسجيل أو تقييم صوتي للمتعلم.
- لا تُرفع تقارير حساسة دون موافقة.
