# الإصدارات والاختبارات — Fluently

## 1. سياسة الإصدارات
- المستخدمون يحصلون على إصدارات مستقرة فقط.
- إصدارات الاختبار داخلية للمطورين ولا تصل للمستخدمين.
- لا توجد فترات تجريبية لخدمات مدفوعة.
- التطبيق والمنهج لهما إصدارات منفصلة.
- يتضمن إصدار Android وWindows المستقر نسخة كاملة من المنهج المنشور وقت بناء التطبيق؛ الويب ينزل المنهج عند أول استخدام. تحديث المحتوى بعد التثبيت يبقى مستقلًا ما دام المخطط متوافقًا.
- تغيير مخطط محتوى غير متوافق قد يتطلب إصدار تطبيق جديد.
- كل إصدار يجب أن يملك changelog ومعرف بناء ومعلومات توافق.

## 2. أنواع الإصدارات
- **Development:** بناء يومي أو فرعي داخلي.
- **Internal QA:** اختبار داخلي لا يوزع على المستخدمين.
- **Release Candidate:** نسخة مرشحة تُختبر في بيئة داخلية.
- **Stable:** إصدار معتمد للمستخدمين.
- **Content Release:** إصدار حزمة منهج مستقل عن إصدار التطبيق.

لا يُسمى اختبار داخليًا "تجربة مجانية"؛ فهو عملية تطوير داخلية لا اشتراك خدمة.

## 3. ترقيم الإصدارات
- التطبيق يستخدم SemVer حيثما كان مناسبًا: MAJOR.MINOR.PATCH.
- حزم المحتوى لها content version مستقلة.
- مخططات البيانات لها schema version.
- إصدار محرك المراجعة ومحرك التقييم يُسجل عند الحاجة.
- كل نتيجة اختبار تحفظ مخطط الاختبار وحدود النجاح المستخدمة وقت المحاولة.

## 4. بوابات النشر
لا يمر الإصدار إلى Stable قبل:
1. نجاح التنسيق وفحص الأنواع والبناء.
2. نجاح اختبارات الوحدات والتكامل.
3. نجاح اختبارات PWA/Android/Windows ذات الصلة.
4. نجاح اختبارات Offline والتخزين والمزامنة.
5. مراجعة أمنية للتغييرات الحساسة.
6. فحص التراخيص والمكونات الخارجية.
7. فحص الحزم والصوتيات.
8. مراجعة المحتوى التعليمي عند تغيره.
9. فحص متطلبات مساحة التثبيت والتنزيل.
10. إعداد ملاحظات التغيير وخطة التراجع.
11. التحقق من وجود المنهج المنشور كاملًا داخل APK/توزيع Windows، ومن مسار تنزيله الأولي على Web/PWA، والتحقق من بصمات الحزمة المضمّنة.

## 5. استراتيجية الاختبارات

### Unit
- محرك المنهج.
- ترتيب المتطلبات السابقة.
- التصحيح.
- الإتقان.
- المراجعة المتباعدة.
- التحقق من الحزم.
- معالجة التعارض.

### Integration
- REST API وقاعدة البيانات.
- المصادقة والتفويض.
- تنزيل الحزم.
- طابور المزامنة.
- تخزين الملفات.
- حذف الحساب.
- إصدار المحتوى والنشر.

### End-to-End
- تسجيل الدخول.
- البدء من الصفر.
- تحديد المستوى.
- فتح الدرس وإكماله.
- اختبار وفشل وخطة علاج.
- مراجعة مستحقة.
- تحديث حزمة.
- تصدير بيانات.
- بلاغ دعم.

### Offline
- قطع الشبكة في منتصف الدرس.
- استمرار الدروس والاختبارات.
- تنزيل منقطع واستئناف.
- مساحة غير كافية.
- فقدان تخزين المتصفح.
- مزامنة جهازين.
- إعادة إرسال عملية لمنع التكرار.
- تعارض لا يمكن دمجه.
- حذف حساب وجهاز آخر غير متصل.

### Security
- تجاوز صلاحيات الإدارة.
- الوصول لسجل متعلم آخر.
- محاولات دخول متكررة.
- جلسات منتهية أو ملغاة.
- XSS وCSRF وSQL injection حيث ينطبق.
- رفع ملف خبيث أو ZIP traversal.
- حزمة معدلة أو غير موقعة.
- تسريب أسرار في logs أو crash reports.

### Accessibility
- لوحة مفاتيح.
- قارئ شاشة.
- تباين.
- تكبير.
- RTL/LTR.
- تقليل الحركة.
- نصوص مرافقة للصوت.
- إكمال رحلة درس دون استخدام الفأرة.

## 6. مصفوفة المنصات
تُطبق التفاصيل والبوابات المحددة في [متطلبات المنصات](PLATFORM-REQUIREMENTS.md)، وهي مرجع الأذونات والتخزين والتحديث والتوقيع لكل منصة.

يُختبر كل إصدار مؤثر على:
- Web/PWA في المتصفحات المستهدفة.
- Android على جهاز فعلي واحد على الأقل لكل فئة دعم أساسية، مع محاكيات عند الحاجة.
- Windows على تثبيت نظيف وتحديث فوق إصدار سابق.

لا يُكتفى بنجاح build؛ يجب اختبار التثبيت والتحديث والتخزين المحلي وتشغيل الصوت والعمل دون اتصال.

## 7. المحتوى والحزم
قبل نشر حزمة:
- تحقق JSON schemas.
- عدم تكرار IDs.
- جميع مراجع الوسائط موجودة.
- البصمات صحيحة.
- لا ملفات تنفيذية أو مسارات مشبوهة.
- تحقق التراخيص والإسناد.
- لا IPA.
- لا أسئلة غير مكتملة الإجابة أو التفسير.
- مراجعة بشرية.
- manifest متوافق مع التطبيق.
- اختبار تنزيل وتثبيت وتراجع.

## 8. التوزيع
- Android: APK موقع بمفتاح محفوظ بأمان خارج المستودع. يجب أن يحتوي إصدار التوزيع المستقر على المنهج المنشور كاملًا، وأن تُفحص بصمات الحزمة المضمّنة. فقدان مفتاح التوقيع قد يمنع تحديث التطبيق بنفس الهوية.
- Windows: EXE وملاحظات إصدار. توثيق حالة التوقيع الرقمي؛ قد يظهر تحذير Windows عند غياب شهادة موثوقة.
- Web: نشر الإصدار الثابت والحزم مع cache/versioning مناسبين.
- الاحتفاظ بملفات الإصدار وبصماتها وملاحظات التغيير.

## 9. خطة التراجع
- لا تستبدل حزمة نشطة قبل التحقق من الجديدة.
- احتفظ بنسخة من آخر حزمة منشورة سليمة.
- إذا فشل إصدار محتوى، عُد إلى إصدار سابق مع manifest واضح.
- إذا فشل إصدار تطبيق، وثّق الإصدار المتأثر وخطوات الإصلاح/إعادة التوزيع.
- اختبر التراجع، ولا تفترض أنه يعمل.

## 10. معايير الإيقاف
أوقف النشر إذا:
- يوجد تسرب بيانات أو تجاوز صلاحيات.
- يوجد فقد تقدم في سيناريو مزامنة.
- حزمة غير صالحة أو غير متوافقة.
- الحقوق غير واضحة.
- محتوى تعليمي منشور دون مراجعة مطلوبة.
- أحد المسارات الأساسية يتطلب خدمة مدفوعة أو تجربة.
- التثبيت أو التحديث يكسر بيانات المتعلم.
