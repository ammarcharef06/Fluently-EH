# معمارية النظام — Fluently

**الحالة:** تصميم معماري مستهدف قبل التنفيذ.  
**مبدأ أساسي:** فصل تطبيقات المستخدم عن محرك المنهج والبيانات والمزامنة ومزودي الخدمات الخارجية.

## 1. المتطلبات المعمارية

- تطبيق موحد متعدد المنصات: Web/PWA وAndroid وWindows.
- استمرار الوظائف التعليمية الأساسية دون اتصال بعد تسجيل الدخول الأول وتنزيل المنهج.
- واجهات API محددة وقابلة للتوثيق والاختبار.
- إمكانية تبديل مزود قاعدة البيانات/التخزين/البريد دون إعادة كتابة منطق المنتج.
- منع تسرب أسرار الخادم إلى تطبيقات المستخدم.
- فصل محتوى المنهج عن بيانات المتعلم وعن بيانات الإدارة.
- بناء تدريجي مع إمكانية إصدار المنهج بصورة مستقلة عن التطبيق.
- لا تعتمد الدراسة الأساسية على استدعاء نموذج ذكاء اصطناعي أو خدمة مدفوعة.

## 2. المنصات والتقنيات المستهدفة

| الطبقة | التقنية المستهدفة | المسؤولية |
|---|---|---|
| واجهة مشتركة | React + TypeScript | مكونات وتجربة المستخدم |
| الويب | PWA | التثبيت الاختياري والتنزيل والعمل دون اتصال |
| Android | Capacitor | تغليف الواجهة وتوفير تكاملات الجهاز المطلوبة |
| Windows | Tauri | تطبيق سطح مكتب مع واجهة الويب |
| API | Hono + TypeScript | المصادقة والتفويض والمزامنة وإدارة المحتوى |
| بيئة API | Cloudflare Workers | تشغيل واجهات API |
| قاعدة البيانات | PostgreSQL عبر Neon | الحسابات والتقدم والبيانات المنظمة |
| اتصال قاعدة البيانات | Hyperdrive عند ملاءمته | تجميع الاتصالات وتحسين الاتصال من Workers |
| تخزين الويب المحلي | IndexedDB | المحتوى والتقدم والعمليات المحلية |
| تخزين التطبيقات | SQLite | قاعدة البيانات المحلية في Android وWindows |
| تخزين الملفات | واجهة تجريد Object Storage | حزم المنهج والوسائط والتحديثات |
| مواصفات API | REST + OpenAPI | عقد ثابت بين التطبيقات والخادم |

هذه التقنيات مستهدفة وليست بعد اختيارات مكتبات دقيقة أو إصدارات ثابتة. تعتمد الإصدارات بعد اختبار توافقها مع المنصات الثلاث.

تُفصّل [متطلبات المنصات](PLATFORM-REQUIREMENTS.md) سلوك Service Worker ومساحة PWA، وأذونات Android ودورة حياته وتحديث APK، وتخزين Windows وتحديث Tauri والتوقيع والجدار الناري. يجب أن تعكس اختبارات القبول تلك الفروق بدل الاكتفاء باختبار الواجهة المشتركة.

## 3. حدود النظام

### 3.1 تطبيق المتعلم
مسؤول عن:
- العرض والتنقل وإدارة الدرس.
- تشغيل المحتوى المنزّل.
- تنفيذ التمارين والتقييمات المحلية.
- عرض التقدم والخطة والمراجعات.
- تخزين العمليات في قاعدة محلية.
- إرسال العمليات للمزامنة عند الاتصال.

لا يحتوي على أسرار الخادم أو صلاحيات إدارة عامة.

### 3.2 لوحة الإدارة
تطبيق ويب مستقل منطقيًا وتقنيًا في workspace باسم `apps/admin`، له مدخل بناء وحزمة نشر منفصلان عن `apps/web`. يمكن نشر التطبيقين على النطاق نفسه (مثل `/admin`) أو على نطاقين، لكن لا يدمجان في تطبيق المتعلم ولا تدخل واجهة الإدارة في حزمة PWA الخاصة به. يعيد `apps/admin` استخدام حزم `packages/ui` و`packages/i18n` وعميل API والحزم المشتركة المناسبة.
مسؤولياته:
- إدارة المحتوى والقوالب وبنك الأسئلة.
- إدارة الموظفين والأدوار.
- مراجعة المحتوى وإصداراته.
- إنشاء الحزم ونشرها واسترجاع إصدار سابق.
- إحصائيات المتعلمين والبلاغات وسجل التدقيق.

يُنشأ هيكل `apps/admin` ومدخل البناء وCI الأساسي في المرحلة 2، دون تنفيذ لوحة الوظائف كاملة. تُنفذ وظائف الإدارة ومحرر المحتوى في المرحلة 7. لا تُعد لوحة الإدارة جزءًا من وظائف المتعلم دون اتصال.

وجود زر مخفي أو مسار غير معلن ليس حماية؛ كل عملية إدارية تتحقق من صلاحية الحساب على الخادم.

### 3.3 محرك المنهج
مكتبة مشتركة لا تعتمد على React أو مزود سحابي. مسؤولة عن:
- قراءة مخططات الدروس والحزم.
- ترتيب المتطلبات السابقة.
- حساب إكمال الأنشطة.
- التحقق من أهلية فتح وحدة/درس.
- توفير بيانات العرض لتطبيق المتعلم.

### 3.4 محرك التقييم
مسؤول عن:
- تنفيذ مخططات الاختبارات.
- تصحيح الأنواع المدعومة.
- إنتاج التغذية الراجعة.
- تسجيل المحاولات والإتقان.
- إنشاء خطة علاجية من نتائج محددة.

يجب أن تكون قواعد التصحيح الأساسية قابلة للعمل دون اتصال. لا يتضمن تقييمًا لصوت المتعلم.

### 3.5 محرك المراجعة
مسؤول عن جدولة العناصر المستحقة، حفظ سجل الأداء، وتقديم مراجعات محلية. الخوارزمية لها إصدار مستقل حتى تتغير لاحقًا دون كسر سجلات المتعلمين.

### 3.6 طبقة التخزين
واجهات مستقلة:
- `CurriculumPackageStore`: تنزيل حزم المنهج وإصداراتها.
- `MediaStore`: الصوت والصور.
- `ProgressStore`: البيانات المحلية والسحابية.
- `BackupStore`: النسخ الاحتياطية والتصدير.

تُختبر واجهة التجريد ضد مزود محلي/اختباري قبل اعتماد Neon Object Storage أو R2 أو أي مزود آخر.

## 4. وحدات منطقية مقترحة

- `apps/web`: تطبيق PWA.
- `apps/mobile`: Android عبر Capacitor.
- `apps/desktop`: Windows عبر Tauri.
- `apps/admin`: تطبيق ويب إداري مستقل بمدخل بناء منفصل، يشارك الحزم المشتركة ولا يشارك ناتج بناء تطبيق المتعلم.
- `packages/ui`: نظام التصميم والمكونات.
- `packages/i18n`: الترجمة واتجاه RTL/LTR.
- `packages/curriculum-engine`: قراءة المنهج والمتطلبات.
- `packages/assessment-engine`: الأسئلة والتصحيح والإتقان.
- `packages/review-engine`: المراجعة المتباعدة.
- `packages/local-data`: الوصول إلى التخزين المحلي.
- `packages/sync-engine`: طابور العمليات وحل التعارض.
- `packages/content-schema`: مخططات JSON والحزم.
- `packages/audio`: فهرس الصوتيات والتشغيل.
- `services/api`: Hono Workers API.
- `content`: حزم المنهج والمفردات والأسئلة.
- `infra`: إعدادات النشر والبنية.

هذه بنية منطقية مقترحة؛ لا تُنشأ جميع الحزم فارغة لمجرد ملء الشجرة. تنشأ عند بدء المرحلة التي تحتاجها.

## 5. حدود الخادم وواجهات API

المجموعات المنطقية:
- المصادقة والجلسات.
- ملف المتعلم وإعداداته.
- المزامنة وسجل العمليات.
- تنزيل manifest وحزم المحتوى.
- حالة إصدار المنهج والتحديثات.
- لوحة الإدارة والمحتوى.
- المراجعة والنشر.
- البلاغات والدعم.
- حذف الحساب وتصدير البيانات.

كل واجهة يجب أن تحدد:
- طريقة HTTP ومسارًا وإصدارًا.
- مخطط الطلب والاستجابة.
- متطلبات المصادقة والتفويض.
- حدود المعدل وحجم الطلب.
- رموز الأخطاء المتوقعة.
- سلوك إعادة المحاولة/idempotency.
- سجلًا لا يحتوي بيانات حساسة.

## 6. قاعدة البيانات

PostgreSQL تخزن البيانات المنظمة:
- حسابات وربط الهوية.
- ملفات المتعلمين وإعداداتهم.
- التقدم والإتقان والمحاولات.
- سجل المراجعة.
- طوابير المزامنة أو مؤشرات العمليات.
- أدوار الموظفين وصلاحياتهم.
- بيانات المحتوى وإصداراته وحالة المراجعة.
- إصدارات الحزم وبيانات النشر.
- البلاغات وسجل التدقيق.

لا تخزن ملفات الصوت والصور الكبيرة داخل PostgreSQL افتراضيًا؛ تستخدم طبقة تخزين الملفات.

## 7. مبادئ فصل البيانات

1. محتوى المنهج إصدار مستقل يمكن تنزيله.
2. تقدم المتعلم منفصل عن المحتوى.
3. هوية الحساب منفصلة عن بيانات التعلم قدر الإمكان.
4. سجل الإدارة منفصل عن سجل المتعلم.
5. لا تُصدّر بيانات المتعلم مع حزمة المنهج.
6. لا تتضمن سجلات الأعطال إجابات أو محتوى شخصيًا.
7. لا تُضمّن الأسرار في تطبيقات المستخدم أو الحزم.

## 8. المصادقة والتكاملات

- دخول Google أو البريد وكلمة المرور.
- تأكيد البريد للحسابات التي تستخدم كلمة المرور قبل المزامنة.
- يتطلب الدخول الأول اتصالًا.
- مزود الهوية والبريد غير محسومين حتى التحقق من شرط عدم البطاقة والفوترة والفترات التجريبية.
- لا يُسمح بتسريب رموز الوصول الدائمة إلى التخزين غير الآمن.
- لا تستخدم مفاتيح إدارية في تطبيق المتعلم.

## 9. الإصدارات والتوافق

- إصدار التطبيق مستقل عن إصدار المنهج.
- كل حزمة منهج لها schema version وcontent version.
- كل تطبيق يعلن نطاق إصدارات المخططات التي يستطيع قراءتها.
- التغيير غير المتوافق يتطلب ترقية التطبيق أو مسار تحويل موثق.
- لا تُحذف حقول أو معرفات مستخدمة من نسخ منشورة دون خطة توافق.

## 10. حدود الموارد المجانية

الخطة المجانية ليست SLA ولا ضمان استمرارية. يجب:
- مراقبة الطلبات والتخزين والنقل.
- منع تفعيل الفوترة التلقائية.
- إظهار تجاوز الحدود للمسؤول.
- اختبار سلوك التوقف والعودة.
- الحفاظ على نسخة تصدير مستقلة.
- دعم نقل قاعدة البيانات والملفات إلى مزود آخر.

## 11. قرارات معمارية مؤجلة
- مكتبة إدارة الحالة والبيانات في الواجهة.
- ORM أو SQL query layer.
- مزود الهوية والبريد.
- محرك TTS والأصوات.
- مزود Object Storage النهائي.
- طريقة توقيع الحزم وتوزيع مفاتيح الثقة.
- استراتيجية احتفاظ/استعادة قاعدة البيانات.
- القياس والتحليلات المسموح بها.

## 12. شروط قبول المعمارية
- يمكن تشغيل محرك المنهج من حزمة محلية دون API.
- يمكن إجراء درس واختبار أساسي دون اتصال.
- يمكن تبديل مزود Object Storage عبر Adapter دون تعديل منطق الدروس.
- لا يصل تطبيق المستخدم مباشرة إلى قاعدة البيانات المركزية.
- كل عملية إدارة تتحقق من الدور على الخادم.
- كل حزمة قابلة للتحقق من الإصدار والبصمات.
- يمكن نقل البيانات من مزود Neon إلى PostgreSQL متوافق دون تغيير نموذج المنتج.
