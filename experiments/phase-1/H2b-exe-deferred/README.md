# H2b — Windows EXE + Authenticode

**الحالة التاريخية:** كان H2b مؤجلًا بقرار بتاريخ 2026-11-01، وليس فشلًا.  
**الحالة الحالية:** أعاد المالك فتح مسار التنفيذ والاختبار بتاريخ 2026-11-02 عبر DECISIONS E-14. أُضيف Tauri shell وبناء EXE غير موقع، واجتاز NSIS install/launch smoke في CI run [41675891966](https://github.com/ammarcharef06/Fluently-EH/actions/runs/41675891966) على commit `12ac6b480e3fe062968e9419036405f2326123a4`؛ سجل التقرير `Result: PASS` ونافذة `Fluently`. دُمج PR #27 في `2968db1d6bfa0408bdaaeb1689fbc339553e55d7`. اكتمل H2b-4 عبر PR #29 ودُمج في `c09167f14451da0e4630766ad72b657c0609720d`. اجتاز CI run [41703166428](https://github.com/ammarcharef06/Fluently-EH/actions/runs/41703166428) (run 178) Windows build/install/runtime/tamper smoke، ثم اجتازت المرحلة المراجعة الفنية المستقلة. CI ما بعد الدمج run [41708362480](https://github.com/ammarcharef06/Fluently-EH/actions/runs/41708362480) (run 179) اجتاز `validate`، وكانت وظيفة Windows قيد التنفيذ عند آخر تحقق. fixture اختبارية غير منشورة وليست المنهج المعتمد؛ H2b-5/SQLite لا تزال غير منفذة.  
**تاريخ تحديث الحالة:** 2026-11-03.

## السؤال التقني المفتوح

هل يمكن بناء تطبيق Tauri/Windows وتضمين حزمة المنهج والتحقق منها وقت التشغيل، ورفض الحزمة المعدّلة داخل التوزيع؟

توقيع Authenticode شرط توزيع مستقل؛ لا يمنع بدء بناء QA أو اختبار سلامة المحتوى، ولا يجوز الادعاء بأن ملف QA غير الموقع موقّع أو صالح كإصدار مستقر.

## سبب التأجيل التاريخي

- لم تكن بيئة Rust/Tauri/Windows قد تم التحقق منها.
- لم تكن شهادة Authenticode موثوقة متاحة، ولم يكن هناك تفويض لشراء شهادة أو خدمة توقيع.
- نجاح H2a على Android لا يقدم دليلًا على Windows أو EXE.

## أثر قرار المالك E-14

فُتح التنفيذ الفني لـ Windows دون شراء شهادة أو خدمة. يمكن بناء ملف QA غير موقع واختباره على Windows مع نشر SHA-256 وتوضيح أنه غير موقع. يظل توزيع إصدار مستقر خاضعًا لمتطلبات PLATFORM-REQUIREMENTS وRELEASE-AND-TESTING وحسم توقيع موثوق أو تصريح واضح بمسار التوزيع غير الموقع؛ ولا يتم أي إنفاق دون تفويض مستقل.

## الحالة المعتمدة بعد E-14

**قيد الإثبات — H2b-3 وH2b-4 اجتازتا بوابتيهما المحددتين.** اجتاز H2b-3 اختبار التثبيت والتشغيل في CI run 41675891966. اجتاز H2b-4 بناء Windows QA وتثبيته وتشغيله بالحزمة السليمة، ورفض التشغيل بعد تعديل بايت واحد من ملف الدرس المثبت برمز خروج 1، ثم نجاح التشغيل بعد استعادة الملف الأصلي في CI run 41703166428 (run 178)، واجتاز المراجعة الفنية المستقلة ودُمج PR #29. لا يعني ذلك اكتمال H2b؛ H2b-5/SQLite لم تُنفذ، والـ fixture ليست المنهج المنشور.

## شروط إثبات H2b الوظيفي

1. **بيئة Windows قابلة للتكرار:** Windows runner بإصدار موثق، مع Rust/Cargo وTauri وNode وWebView2 بإصدارات متوافقة، وصلاحية بناء وتثبيت وتشغيل artifact على Windows أو VM مدعوم.
2. **مسار تقني قابل للإثبات:** بناء EXE/installer، تضمين payload اختبار، قراءة التطبيق له من داخل التوزيع، واختبار checksum سليم/معدل ورفض التفعيل عند تغيير بايت واحد، مع قياس الحجم وزمن البناء والتثبيت/الإطلاق. لا يكفي نجاح build وحده.

## خطوة H2b-1 — فحص بيئة Windows

أُضيف سير عمل `.github/workflows/ci.yml` على `windows-2025` ليتحقق من Node.js `22.16.0` وRust `1.99.1` وهدف MSVC x64، ووجود Visual Studio C++ Build Tools وWebView2 Evergreen Runtime. يحفظ التقرير كـ artifact لمدة 30 يومًا.

هذه الخطوة **فحص بيئة فقط**؛ لا تبني Tauri ولا EXE ولا تثبت التطبيق ولا تختبر قراءة payload أو tamper. تظل H2b «غير مُثبت» حتى اجتياز جميع شروطها الوظيفية على Windows.

## بوابة Authenticode المنفصلة

- توقيع Authenticode الموثوق مطلوب بحسب شروط التوزيع المستقر عندما تتوفر شهادة/خدمة موثوقة ومصرح بها.
- لا يجيز E-14 شراء شهادة أو خدمة توقيع. لا تُخزن مفاتيح التوقيع في Git.
- يمكن استخدام EXE غير موقع لاختبارات QA فقط، مع SHA-256 وإشعار صريح بأنه غير موقع؛ لا يسمى إصدارًا مستقرًا ولا يدعى أنه اجتاز Authenticode.
- لا يبدأ تحديث Windows التلقائي قبل استقرار المنصات الثلاث وحسم آلية الثقة والتوقيع.

يُسجل نجاح الجزء الوظيفي H2b مستقلًا عن بوابة التوزيع والتوقيع. لا يعني استيفاء build وحده اجتياز runtime/tamper، ولا يعني اجتياز الاختبار الوظيفي أن ملف التوزيع موقّع.

## خطوة H2b-2 — هيكل Tauri وبناء QA أولي

أُضيفت `apps/desktop/src-tauri` كتطبيق Tauri 2، ويحمّل واجهة المتعلم الحالية من `apps/web` بدل إنشاء واجهة React منفصلة. الإصدارات المثبتة في manifest هي Tauri Rust `2.12.5` وTauri CLI `2.12.4`، مع Rust toolchain `1.99.1` من فحص البيئة السابق. أضيف إلى CI بناء Windows باستخدام `tauri build --no-bundle` ورفع EXE غير موقع كـ artifact داخلي قصير الاحتفاظ.

**حدود هذه الخطوة:** نجاح بناء EXE لا يثبت تثبيته أو تشغيله على Windows، ولا يثبت تضمين المنهج أو SQLite أو runtime-read أو رفض العبث. لا يُسمح بتوزيع artifact على المتعلمين، ولا يدعي توقيع Authenticode. يجب أن يظل `apps/desktop/src-tauri/Cargo.lock` الملتزم به هو مرجع البناء؛ يتحقق CI باستخدام `cargo check --locked` ولا يكتب إلى فرع PR. يُرفع artifact للملف كأثر توثيقي فقط، وليس بديلًا عن lockfile الملتزم به.


## خطوة H2b-3 — مثبت QA واختبار التثبيت والتشغيل

أُضيف إلى إعداد Tauri وضع NSIS صريح `currentUser`، بما يطابق متطلب تجنب صلاحيات Administrator وحفظ التثبيت ضمن مساحة المستخدم. يبني CI مثبت NSIS وEXE، ثم يشغّل `scripts/windows/qa-install-smoke.ps1` على `windows-2025`.

ينفذ الاختبار الآلي الخطوات التالية:
1. يثبت مثبت NSIS بصمت في مجلد QA داخل `%LOCALAPPDATA%` للمستخدم الحالي.
2. يتحقق من وجود `fluently-desktop.exe` بعد التثبيت.
3. يشغل الملف المثبت ويتحقق من بقاء العملية وظهور نافذة رئيسية عنوانها يتضمن `Fluently` خلال المهلة المحددة.
4. يسجل SHA-256 للمثبت والملف التنفيذي، وحجم المثبت، ومسار التثبيت، ومعرف العملية وعنوان النافذة كـ artifact مستقل.

**حدود H2b-3:** هذا اختبار تثبيت/إقلاع على صورة Windows runner محددة فقط (CI run 41675891966، PR #27، merge commit `2968db1d6bfa0408bdaaeb1689fbc339553e55d7`)، ولا يثبت تجربة مستخدم فعلية على أجهزة متنوعة. لا يثبت بعد قراءة حزمة منهج مضمّنة أو التحقق من بصمتها أو رفض نسخة معدلة، ولا SQLite أو Offline lesson flow أو Authenticode. لا يُوزع أي artifact غير موقع على المتعلمين. تظل H2b غير مُثبت حتى اجتياز كل شروطها الوظيفية.


## ترتيب H2b الداخلي — توضيح SQLite

هذا الترتيب يثبت موقع SQLite صراحةً ولا يغيّر التسلسل الجاري:

- **H2b-1:** فحص بيئة Windows.
- **H2b-2:** Tauri shell وبناء QA.
- **H2b-3:** NSIS installer واختبار تثبيت التطبيق المثبّت وتشغيله.
- **H2b-4:** تضمين حزمة المنهج والتحقق من manifest وSHA-256 ورفض التلاعب.
- **H2b-5:** إكمال SQLite الأصلي وربطه بتقدم المتعلم في Windows.

### قبول H2b-5 — حفظ التقدم واسترجاعه بعد إعادة التشغيل

1. ثبّت artifact Windows الذي اجتاز H2b-3؛ لا تستخدم تشغيل dev server أو mock بدل النسخة المثبّتة.
2. ابدأ بقاعدة SQLite جديدة، وأنشئ/حدّث تقدمًا لمتعلم ودرس بمعرّفات ثابتة عبر رحلة التطبيق الفعلية.
3. احفظ حالة التقدم المطلوبة، ثم أغلق التطبيق بالكامل وتأكد من انتهاء عمليته.
4. افصل الشبكة وأعد تشغيل التطبيق المثبّت.
5. افتح المتعلم/الدرس نفسه وتحقق من استرجاع القيم المحفوظة من SQLite الفعلية، بما فيها هوية المتعلم والدرس وحالة الإكمال والإجابات/النقاط والطابع الزمني، دون إعادة إدخالها.
6. أعد الاختبار على قاعدة من schema سابق بعد تشغيل migration؛ تحقق من بقاء البيانات وعدم تكرار السجلات أو فقدها.
7. احتفظ بتقرير الاختبار، وإصدار schema قبل/بعد، وسجل migration، وبصمة ملف قاعدة الاختبار المنقّح من أي بيانات شخصية. لا ترفع بيانات متعلم حقيقية إلى CI.

اختبارات الوحدات والتكامل للمخزن مطلوبة، لكنها لا تستبدل هذا الاختبار على التطبيق المثبّت. لا تُعد H2b مكتملة قبل نجاح H2b-3 وH2b-4 وH2b-5 معًا؛ توقيع Authenticode يظل بوابة توزيع مستقلة كما هو موثق أعلاه. SQLite مؤجل إلى H2b-5، وليس إلى H3 ولا إلى مسار Android اللاحق.


## خطوة H2b-4 — حزمة اختبار مضمّنة والتحقق وقت التشغيل

أضيفت في PR #29 حزمة fixture صغيرة داخل موارد Tauri:
- `resources/curriculum/manifest.json`
- `resources/curriculum/lessons/pre-a1-integrity-fixture.json`

هذه **ليست منهجًا منشورًا أو معتمدًا**؛ الدرس موسوم `draft` والغرض منه اختبار سلامة الملفات فقط. يحتوي manifest على معرف الحزمة وإصدار المحتوى والمخطط وحجم الملف وبصمة SHA-256 وبيان الحقوق. يثبت التطبيق بصمة manifest في الكود التنفيذي، ثم يتحقق عند بدء التشغيل من:
1. حجم manifest والملف ضمن الحدود المحددة.
2. تطابق SHA-256 للـ manifest مع القيمة المضمّنة في executable.
3. معرف الحزمة وإصدار المحتوى وإصدار المخطط ومسار الملف الوحيد المتوقع.
4. تطابق حجم الدرس وبصمة SHA-256.
5. صلاحية JSON وبيانات fixture الأساسية، وأن حالته `draft`.

يفشل بدء التطبيق ويخرج برمز غير صفري عند فشل التحقق. تشمل اختبارات Rust قبول fixture الأصلي ورفض تعديل بايت من manifest أو الدرس، ورفض JSON غير صالح والمدخلات المتجاوزة للحدود. ويضيف Windows install smoke اختبارًا على النسخة المثبتة: قبول الموارد السليمة، تعديل بايت واحد من ملف الدرس واشتراط خروج التطبيق بخطأ، ثم استعادة الملف الأصلي وإثبات نجاح التشغيل مجددًا.

**الحدود:** هذا إثبات سلامة fixture واحدة فقط، وليس تضمين المنهج المنشور كاملًا أو تشغيل درس للمتعلم أو إثبات SQLite. بصمة manifest المضمّنة تثبت سلامة الموارد بالنسبة إلى executable الحالي؛ ليست توقيعًا رقميًا ولا تحمي من استبدال executable أو ترقيعه. Authenticode يظل بوابة توزيع مستقلة. اجتاز Windows CI run 41703166428 (run 178) وأدلة artifact المثبت، واجتاز المراجعة الفنية المستقلة ثم دُمج PR #29. لا تزال H2b-5/SQLite مطلوبة قبل قبول H2b بالكامل.
