# H2a — بناء APK عبر CI وقراءة placeholder من داخل التطبيق

**الحالة قبل التنفيذ:** المعايير مسجلة؛ لا توجد نتيجة بعد.  
**تاريخ تسجيل المعايير:** 2026-11-01.  
**الموعد النهائي:** 2026-11-08، 23:59 بتوقيت Africa/Algiers.  
**النطاق:** Android APK عبر Capacitor على GitHub Actions. لا يشمل Windows/Tauri.

## السؤال القابل للتكذيب

هل تنتج سلسلة CI نظيفة APK قابلًا للتثبيت والتشغيل، يحتوي placeholder بالحجم المحدد، ويقرأ التطبيق الملف من داخل أصول APK ويطبع SHA-256 مطابقًا للأصل؟

## حدود الشاهد

هذا الشاهد يثبت سلسلة APK على runner Ubuntu محدد فقط. لا يثبت أن البنية تعمل على جهاز المطور المحلي، ولا يثبت EXE/Windows، ولا توقيع إصدار Android الإنتاجي. لا يُدمج أي جزء منه تلقائيًا في تطبيق Fluently.

## معايير النجاح المسجلة قبل أول تشغيل

**H2a = نجاح** فقط عند اكتمال كل البنود التالية:

1. **بناء CI نظيف:** يكتمل بناء APK على runner مُدار جديد دون خطوات يدوية أو أسرار خاصة بالمشروع.
2. **احتواء payload:** يحتوي APK النهائي على placeholder.bin كاملًا بحجم **134,217,728 بايت (128 MiB)**. يُولد الملف عالي الإنتروبيا على runner حتى لا يعطي ضغط ZIP تقديرًا زائفًا.
3. **التثبيت والتشغيل:** يُثبت APK ويُطلق على Android Emulator واحد على الأقل. يُنفذ ذلك في job مستقل عن job البناء.
4. **قراءة runtime:** يقرأ التطبيق الملف باستخدام Android AssetManager من داخل APK المثبت، لا من الشبكة ولا من مسار خارجي، ويطبع في Logcat قيمة SHA-256 وحجم الملف.
5. **مطابقة checksum:** تتطابق قيمة SHA-256 المطبوعة من داخل التطبيق مع القيمة المحسوبة من ملف الإنشاء قبل التغليف.
6. **الأرقام الإلزامية:** تسجل الأدلة حجم APK النهائي بالبايت وMiB، زمن Gradle build بالثواني، زمن adb install بالثواني، زمن الإطلاق/ظهور checksum، حجم placeholder، وقيمته SHA-256.
7. **البيئة القابلة للتكرار:** تسجل الأدلة صورة runner الفعلية وإصدارات Node/npm وJDK وAndroid SDK/Build Tools وGradle Wrapper وAndroid Gradle Plugin (AGP) وCapacitor، مع الاحتفاظ بـ Gradle logs.
8. **نوع التوقيع:** H2a يقيس **debug signing فقط**. لا يثبت قابلية توقيع إصدار Android الإنتاجي أو نشره.

## حالات النتيجة

- **نجاح:** تحققت البنود 1–8، مع بناء وتثبيت وتشغيل وقراءة checksum ناجحة.
- **جزئي:** نجح البناء واحتوى APK على placeholder، لكن تعطل التثبيت/الإقلاع بسبب emulator أو KVM أو بنية CI. يسجل حجم APK وزمن البناء والسبب والـlogs؛ لا يسمى نجاح H2a.
- **فشل حقيقي:** أخفق البناء أو لم يحتو APK الملف كاملًا أو لم يقرأ التطبيق الملف أو اختلف checksum، أو تطلبت السلسلة أسرارًا أو خطوات يدوية غير موثقة.
- **تعذّر الإثبات:** انتهى الموعد أو تعذرت بيئة الاختبار/صلاحياتها دون دليل يثبت نجاحًا أو فشلًا تقنيًا. لا تمديد ضمنيًا.

## فصل الوظائف في CI

- **Job build:** يولد placeholder، ينشئ مشروع Capacitor/Android، يبني APK، يفحص محتواه، يسجل الحجم والزمن والإصدارات، ويرفع APK والأدلة كـ artifact.
- **Job install-on-emulator:** وظيفة مستقلة تنزّل artifact البناء وتثبت APK وتشغله وتتحقق من Logcat.
- **المحاولات:** محاولتان كحد أقصى لتشغيل emulator (الأولى + إعادة واحدة). لكل محاولة حد أقصى 15 دقيقة، والـjob حدّه 25 دقيقة. فشل تشغيل emulator بعد المحاولتين ينتج **جزئي** إذا كان البناء واحتواء placeholder ناجحين.
- لا يعاد بناء APK عند إعادة محاولة emulator؛ يجب اختبار artifact نفسه.

## ما لا يثبته H2a

- لا يثبت التحقق من manifest/signature أو رفض ملف معدل؛ هذا جزء من H4.
- لا يثبت أن الحزمة تمثل المنهج الحقيقي أو أن حجمه النهائي 128 MiB.
- لا يثبت تحديث المحتوى أو rollback.
- لا يثبت Tauri/Windows أو EXE أو Authenticode.
- لا يثبت release signing؛ الاختبار يستخدم debug key.

## تعديل المعايير

أي تعديل لحجم placeholder أو صورة runner أو API level أو timeout أو عدد المحاولات بعد أول تشغيل يجب أن يسجل بالنص: **"تعديل معيار بعد ملاحظة [السبب]"** مع النتيجة الأصلية والجديدة. لا تحذف نتيجة أو محاولة فاشلة.
